# Showcase / Demo Strategy

The `examples/` directory is not a toy. It serves three jobs at once:

1. **Edge-case validation** — every demo stresses parts of the API the unit tests can't reach (timing, backpressure, multi-pane coordination, real terminal output).
2. **Limitation discovery** — when a demo is awkward to write, that awkwardness *is* the feedback. It tells us where the library's shape is wrong, where a missing primitive lives, or where an invariant should be hoisted into the core.
3. **Canonical reference** — these are the examples users will copy from. Treat every line as the public face of the project. No shortcuts, no "good enough for a demo," no `any`, no swallowed errors.

A good demo is one that **could not reasonably exist without tmux control mode** — i.e. would be absurd or impossible with one PTY per pane. Lean into that asymmetry. If the same thing is easy with `node-pty`, it's a weak demo.

---

## Axes of coverage

When picking demos, try to span these axes so the showcase doubles as informal conformance:

| Axis | What it stresses |
|---|---|
| **Throughput** | High-rate output, backpressure, parser perf, frame coalescing |
| **Multiplex breadth** | Many panes, many windows, many sessions at once |
| **Control-mode commands** | `%output`, `%layout-change`, `%window-add`, `%session-changed`, `%exit`, etc. |
| **History / scrollback** | `capture-pane -p -S -` ranges, history search, incremental indexing |
| **Input fidelity** | Keystrokes, paste, mouse, bracketed paste, modifier-encoded keys |
| **State reconciliation** | Reconnect / catchup / out-of-order events |
| **Parsing depth** | ANSI/CSI/OSC/DCS/SGR, Sixel, iTerm/Kitty image protocols, hyperlinks |
| **Recording / replay** | Deterministic byte-stream capture, time-travel debugging |

A demo that hits 3+ axes is gold. A demo that hits 1 is fine if that axis is otherwise uncovered.

## Demo ideas

### Already on the table
- **Full-text search across all pane scrollback** — *ships today* as the "Scrollback Search" mode of `examples/web-multiplexer/`. A trigram inverted index (`web/trigram-index.ts`) is seeded from `capture-pane -p -S - -E -` across every pane in every session and kept live by decoding `%output` into plain text (`web/ansi-text.ts`) and appending incrementally. Stresses: history, throughput, multiplex breadth.
  - *Limitation discovered:* deriving searchable text from the live `%output` byte stream needs ANSI-stripping, but neither `@promptctl/pane-terminal` nor the protocol package exposes a plain-text/line extraction primitive (only byte sinks, the xterm renderer, and `bytesToLatin1` / `decodeOctalEscapes`). The demo ships a local stripper; a reusable "terminal bytes → plain text rows" sink is a candidate primitive for the package. The stripper is line-granular, not a screen model, so `\r`-driven in-place redraws (progress bars, shell prompts) index as their raw concatenation rather than the final rendered line.
  - *Scope discovered:* `capture-pane` backfill reaches every pane on the server, but tmux streams live `%output` only for the **attached** session — so history is global while live updates follow the focused session. The UI states this honestly rather than implying global live indexing.
- **Cross-terminal regex matcher** — *ships today* as the "Regex Matcher" mode of `examples/web-multiplexer/`. A live `tail -f | grep` across every pane in every session at once: a compiled `RegExp` applied per completed line at ingestion (`web/regex-match-engine.ts`, pure + unit-tested), matches streaming into a bounded chronological feed grouped session › window › pane, click-to-jump. Stresses: throughput, multiplex breadth, parsing.
  - *Primitive discovered:* no part of the demo previously streamed more than ONE session's live output — tmux streams live `%output` only for the **attached** session, and the browser can't open tmux connections. "All sessions live" therefore required a NEW bridge-process **firehose**: `PaneFirehose` (`server/pane-firehose.ts`) taps every pane via `pipe-pane` to per-pane FIFOs (verified: reaches panes with zero clients attached), forwarded on a **dedicated channel** separate from attached `%output` (binary frame magic `0xF1` on WebSocket vs the library's `0x7F`; a `demo:firehose-bytes` IPC channel on Electron) so the regex feed is single-source and attached bytes never double-count. Implemented once on the shared `TmuxBridge` contract for BOTH transports.
  - *Axis separation from scrollback search:* search is substring-over-an-indexed-corpus (passive, query-time, trigram-narrowed); this is pattern-first LIVE streaming (a regex can't be trigram-prefiltered in general). Different operation, different axis.
- **Inline image extraction** — *ships today* as the "Image Extractor" mode of `examples/web-multiplexer/`. A streaming sniffer pulls iTerm2 (OSC 1337), Kitty (APC `_G` graphics) and Sixel (DCS) image escape sequences out of the raw byte stream of every pane in every session, decodes them (`web/image-extract-engine.ts`, pure + unit-tested against ImageMagick-generated fixtures), and renders the images in a gallery grouped session › window › pane, click-to-jump. Stresses: parsing depth.
  - *Why the firehose is mandatory, not optional:* tmux's own screen emulator consumes graphics sequences it doesn't render, so the attached `%output` control-mode stream has them **stripped**. Only `pipe-pane` (the `0.2` firehose) taps the pane's pty *before* tmux's emulation, where the sequences survive byte-for-byte (verified live, tmux 3.6a). So this demo reuses `PaneFirehose` as its sole byte source — it does **not** build on `@promptctl/pane-terminal`, whose `PaneStream` sources the stripped `%output` and whose `XtermSink` renders a terminal grid, not decoded images. It is in the same "consumes raw bytes, renders a non-terminal view" family as the Inspector and the planned data sniffer.
  - *Parsing depth discovered:* a single image can be split across arbitrary firehose chunk boundaries — even between the `ESC` and the `\` of a String Terminator — and Kitty deliberately chunks large transfers (`m=1` … `m=0`). The decoder is therefore a resumable per-pane state machine that carries parser state across `pushBytes` calls and reassembles multi-chunk Kitty transfers, not a regex over a buffer. iTerm2 files and Kitty PNGs decode to encoded bytes (rendered via a blob `<img>`); Kitty raw frames and Sixel decode to an RGBA raster (painted to `<canvas>`).
- **Escape-code playground** — *ships today* as the "Escape Playground" mode of `examples/web-multiplexer/`. Type or paste ANSI/escape sequences (with `\e \x1b \033 \n \uHHHH` notation) and watch a real tmux pane render them, three columns side by side: raw bytes (hex + escaped), parsed events (a pure VT classifier — `web/escape-parse-engine.ts`, unit-tested — that labels CSI/SGR/OSC/ESC/DCS and decodes SGR colors into swatches), and the live rendered cells. Stresses: parsing depth, **input fidelity**.
  - *Axis discovered:* this is the only demo that exercises the **outbound** path. Every other demo passively observes `%output`; this one *sends*. The library's `sendKeys` encodes via `send-keys -H utf8HexBytes(s)` — every byte hex-encoded — so arbitrary control bytes (ESC, C0 controls) arrive byte-for-byte; the round-trip you watch is the proof of that fidelity. The playground is string-native by design: the bytes it displays and parses are exactly `TextEncoder.encode(interpreted)`, which is what `send-keys -H` transmits, so for the whole 7-bit ANSI repertoire what you see is what is sent.
  - *Why a scratch pane:* `send-keys` writes to a program's stdin; escape sequences only reach the screen when they appear in the pane's *output*. The playground spawns a dedicated window running `sh -c "stty raw; exec cat"` — a transparent stdin→stdout byte mirror — and sends to it, leaving the user's panes untouched. Killed on leaving the mode.
  - *Control-mode findings (verified live, tmux 3.6a — relevant to any demo that renders a dynamically-created pane):* (1) a control client with no terminal streams live `%output` only for the window it is **currently viewing**, so the playground `select-window`s its scratch window (and restores the prior view on exit) — a detached window's pane never reaches the renderer. (2) `@promptctl/pane-terminal`'s `XtermSink` buffers all bytes until its first `resize(cols,rows)`, which is driven by a per-pane size *subscription* that emits only on a size **change** — a freshly created window never changes size, so the demo queries the pane geometry and calls `sink.resize()` directly to paint the first byte. (3) xterm suspends rendering in a zero-height container, so the column layout must give the terminal a real (floored) height.
- **Record / replay of terminal sessions** — *ships today* as the "Session Recorder" mode of `examples/web-multiplexer/`. Hit Record, let any pane in any session produce output, hit Stop, then scrub the captured byte stream like video: drag the timeline, play at 0.5–4×, watch the terminal reconstruct exactly what was on screen at that moment. A pure, unit-tested engine (`web/session-recording-engine.ts`) holds the recording as an immutable timestamped byte log and reconstructs terminal state at any moment; the store (`web/session-recorder-store.ts`) owns capture + a single playback clock; the view drives an `XtermSink` directly from the scrub position. Stresses: recording, state reconciliation, timing.
  - *Axis discovered:* this is the only demo that captures the firehose **with timing** and reconstructs terminal **state at an arbitrary past moment**. The reconstruction is two pure functions over the log — `bytesUpTo(t)` (all bytes ≤ t, the seek primitive) and `bytesBetween(a, b)` (the forward delta) — with the invariant `bytesUpTo(a) ++ bytesBetween(a, b) === bytesUpTo(b)`, which is what lets playback paint forward deltas and re-seek only on a backward jump. This is the **recording infrastructure** the history demos (`.9` scrollback time machine, `.10` diff-two-moments, `.11` bisect) reduce to: all three are `bytesUpTo` against a shared `Recording`.
  - *Why the firehose, not `%output`:* recording is **view-independent** — it must capture every pane regardless of which window a control client is viewing, and it must capture the bytes the program *wrote*, not tmux's emulated view. That is exactly `pipe-pane` (the `.2` firehose), so this demo reuses `PaneFirehose` as its byte source. It is the asciinema model: record raw pty bytes, replay them into a fresh emulator.
  - *Why the .4 live-pane findings DON'T apply:* the replay surface is **not** a live pane — it is an `XtermSink` the view owns and feeds recorded bytes via `write()`. So there is no `select-window` (no live `%output` is routed) and no resize-on-subscribe race (no `PaneStream` subscription). Only two of the three `.4` findings carry over: the sink still buffers until its **first `resize`**, so the view calls `sink.resize(cols, rows)` directly (from the pane geometry captured at record time via `display-message`); and xterm still suspends in a **zero-height container**, so the surface is floored. Replay falls back to 80×24 for a pane whose geometry query never resolved (it vanished mid-recording).
- **"Who wrote this byte?" attribution** — *ships today* as the "Byte Attribution" mode of `examples/web-multiplexer/`. Hover any cell in a reconstructed terminal grid and see the exact firehose chunk + arrival time + byte offset that produced it; click to pin, toggle "color by chunk" to watch the raw stream carved into cells. A pure, unit-tested VT emulator (`web/byte-attribution-engine.ts`) folds a pane's bytes into a grid where every cell carries its source byte; the store (`web/byte-attribution-store.ts`) taps the firehose and reconstructs the grid; the hover panel classifies the producing chunk with the same VT parser the Escape Playground uses. Stresses: parsing depth, **state reconciliation**.
  - *Why it had to BE the emulator (the axis):* xterm.js is a lossy projection — bytes go in, a grid comes out, and the byte→cell function is discarded inside it, so "who wrote this cell" is **unanswerable** through a rendered `XtermSink`. The only way to keep the mapping is to *be* the terminal emulator: this demo renders its **own** provenance-bearing grid (cursor model, deferred wrap, scroll region, ED/EL/ECH/ICH/DCH/IL/DL, SGR pen) instead of xterm. It is therefore the first render-style demo that does **not** build on `@promptctl/pane-terminal` — it is in the "raw bytes → custom view" family with the Inspector/Image Extractor, not the live-pane family.
  - *Why the firehose, not `%output` (and why the SHOWCASE-stanza tension dissolves):* the original idea said "attribute the rendered cell to its `%output` chunk", which sounds like it must read the same stream `XtermSink` renders. But because this demo reconstructs the grid from the **very bytes it attributes**, the cell and its provenance come from one pass over one stream and **cannot disagree** — so the source is free to be the truest one: the firehose (`pipe-pane`), the program's actual output byte *before* any emulation, all-pane and focus-independent (no `select-window` hijack). The "firehose attributes bytes xterm never rendered" risk only exists if you render via xterm *and* attribute via a separate stream; reconstructing your own grid eliminates it. [LAW:one-source-of-truth]
  - *Parsing depth discovered:* the live firehose splits sequences across arbitrary chunk boundaries — a CSI mid-parameter, or a multi-byte UTF-8 grapheme between its lead and continuation bytes. The emulator carries parser state across chunks and attributes each glyph to the chunk/offset of its **first** byte regardless of where the rest arrived (unit-tested by feeding deliberately-split chunks). This is the tight parser↔grid↔raw-stream integration the demo is named for.
- **Scrollback time machine** — *ships today* as the "Time Machine" mode of `examples/web-multiplexer/`. Hit Record: every pane is first seeded with a `capture-pane -e -p -S - -E -` snapshot (its full scrollback *plus* visible screen, re-encoded by tmux as SGR-bearing rows), then the forward firehose is recorded. In review you drag **one** timeline — left of the "now" marker you scroll *up* through captured scrollback rows; right of it you play *forward* through recorded time — and the terminal reconstructs every moment with full ANSI state. A pure, unit-tested engine (`web/scrollback-engine.ts`) maps a scrub fraction onto a discriminated `Moment` (history-row vs live-ms) and produces the paint bytes; the store (`web/scrollback-store.ts`) owns the capture-then-record ordering and the scrub clock; the view drives an `XtermSink`. Stresses: history capture, state reconciliation, timing.
  - *The axis (`capture-pane -e`):* the only demo that recovers a pane's history the browser **never attached to**. tmux re-encodes the whole scrollback buffer back into escape-bearing text; over control mode each row is a byte-faithful reply line, so the browser rebuilds it into a colored grid it can scrub.
  - *Why a seed closes the `.5` gap:* the Session Recorder replays **only** the forward firehose into a freshly-cleared terminal — silently lossy for any pane that already had content, since the firehose holds only post-Record bytes. Seeding fixes both directions: forward reconstruction becomes `clear ++ seed ++ bytesUpTo(t)` (the real screen, then the delta), and backward scrub has real history to walk into. The two regimes meet seamlessly at t=0 (the bottom history window *equals* the live seed). [LAW:one-source-of-truth]
  - *Ordering discovered:* the seed `capture-pane` calls must **complete before** firehose buffering opens, or a forward byte would be counted twice (once baked into a later seed, once in the stream). The store awaits every capture, then flips to recording — a sub-frame loss gap, surfaced honestly rather than risking a double-count. [LAW:no-ambient-temporal-coupling]

### New ideas

#### Time travel / history
- **"Diff two moments"** — *ships today* as the "Moment Diff" mode of `examples/web-multiplexer/`. Record a session (every pane seeded up front, then the forward firehose), then drag **two** playheads — A (before) and B (after) — over recorded time and see exactly what changed between them: each screen cell classified added / removed / changed / unchanged, plus where the cursor moved. A pure, unit-tested engine (`web/moment-diff-engine.ts`) reconstructs the pane's screen at each moment and diffs the two grids cell-by-cell; the store (`web/moment-diff-store.ts`) owns the capture-then-record ordering and the two playheads; the view paints an owned cell grid tinted by change kind. Useful for debugging a TUI redraw — "what did this frame actually touch?". Stresses: state reconciliation, parsing depth.
  - *Reuse, not re-derivation:* the faithful screen at moment *t* is `emulate(seed ++ bytesUpTo(t))` — so the engine asks `.9`'s `momentBytes` for the exact bytes (the single authority for "how a moment looks") and folds them through `.8`'s owned VT emulator (xterm is lossy; a cell-level diff needs per-cell access). [LAW:single-enforcer]
  - *Why seed BOTH sides with the same seed:* a shared seed makes the diff purely the forward delta between the two times. Seed only one side (the `.5` mistake) and every pre-existing cell reads as "added", burying the real change. Equality compares cell *appearance* (char/fg/bg/bold), never provenance — two moments are always written by different bytes. [LAW:no-silent-failure]
- **Bisect a TUI bug** — *ships today* as the "Bug Bisect" mode of `examples/web-multiplexer/`. Record a session that broke (every pane seeded up front, then the forward firehose), then git-bisect the selected pane's recorded **byte stream**: at each step the reconstructed screen at a midpoint byte offset is shown, you judge "bug present?", and each verdict halves the search until it pins the single byte that broke the screen — which the engine names back to its escape sequence (`ESC [ 2 J`, an OSC, a stray control byte). A pure, unit-tested engine (`web/bisect-engine.ts`) holds the git-bisect reducer + the `emulate(seed ++ stream.slice(0, n))` reconstruction + `culpritSequence` (which reuses `.4`'s `parseEscapes` to tokenize the offending span); the store (`web/bisect-store.ts`) owns the capture-then-record ordering and the bisect state, with the user as the oracle.
  - *Why the BYTE axis, not time:* `.9`/`.10` key reconstruction on recorded time (`tMs`), but one firehose chunk carries one timestamp, so time can't address a point mid-chunk. "Find the offending escape *sequence*" needs resolution finer than a chunk, so the search runs over a byte offset into `paneStreamBytes` (the pane's whole forward stream). [LAW:types-are-the-program]
  - *The oracle is a value, not a branch:* the reducer `recordVerdict(state, "present" | "absent")` is blind to whether a human clicked or a predicate decided, so the same engine drives the interactive demo and the deterministic `autoBisect` used by the tests. The seed assembly is the single `scrollback-engine.seededPaint` (one definition of clear-then-seed-then-forward, shared with the time-keyed `momentBytes`), so the culprit is always in the forward delta, never the seed. [LAW:dataflow-not-control-flow] [LAW:one-source-of-truth]

#### Multiplexing power moves
- **Broadcast input with per-pane transforms** — *ships today* as the "Smart Broadcast" mode of `examples/web-multiplexer/`. Type one template, pick N target panes across any windows/sessions, and send a payload **resolved per pane**: built-in variables (`${pane}`, `${title}`, `${session}`, …) resolve from each pane itself, and user variables (`${host}`, `${user}`, …) take a per-pane value in an override grid. A pure, unit-tested engine (`web/broadcast-engine.ts`) tokenizes the template and resolves it against each pane's bindings; the store (`web/broadcast-store.ts`) derives the built-ins from the live pane model and fans the resolved bytes out over the existing `sendKeys`; the view previews exactly the bytes that go on the wire and sends.
  - *The first WRITE-axis demo:* every other showcase taps a pane's **output**; this drives its **input** (`send-keys -H`). Native tmux broadcast (`synchronize-panes`) sends *identical* keys to *one window's* panes — this resolves a *distinct* command per target across *every* session, which only control mode's `send-keys -t %id` allows. The per-pane transform is a **value** (a binding map); the resolver is blind to whether a binding is a pane fact or a user override, so the demo and the unit tests feed the identical engine. [LAW:dataflow-not-control-flow]
  - *An unbound variable is a loud miss, never `""`:* a referenced `${host}` with no binding makes that pane `unresolved`, names the missing variables, and **excludes it from the send** — a silent empty substitution would fire a half-formed command (`ssh ` with no host) at a real shell. The same resolved value drives both the preview and the wire, so what you read is byte-identical to what is sent (the appended Enter shows as `␍`). [LAW:no-silent-failure] [LAW:one-source-of-truth]
- **Pane-graph dashboard** — render every pane in every session as a tile in a CSS grid, all live, all interactive. With 50+ panes this is a real stress test of the event pipeline.
- **Synchronized scrollback** — *ships today* as the "Sync Scrollback" mode of `examples/web-multiplexer/`. Record a session (every pane seeded up front, then the forward firehose), then drag **one** shared cursor and watch N **linked** panes reconstruct their screen at the **same recorded instant**, in lockstep — or click any pane's activity bar to drive them all from there. A pure, unit-tested engine (`web/sync-engine.ts`) projects the shared recording onto per-pane paint bytes; the store (`web/sync-store.ts`) owns the capture-then-record ordering, the linked-pane set, and the one shared playback clock; the view (`web/components/SyncScrollView.tsx`) renders a grid of `XtermSink`s all fed from the single cursor. Stresses: **multiplex breadth**, state reconciliation, timing.
  - *The axis (cross-pane time sync):* the only demo that scrubs MANY panes on one shared clock. A `Recording` (`.5`) stores every pane's chunks keyed by paneId on **one** wall clock (one control client taps every pane in every session via the firehose), so "what did all these panes look like at t=4.2s?" is answerable from a single recording — impossible with one PTY per pane, where you'd have N unsynchronized clocks. That asymmetry is the demo.
  - *The synchronization coordinate is recorded TIME, not a scroll position:* the `.9` time machine scrubs a pane on a per-pane `[0,1]` axis, but the same fraction is a **different instant** in each pane (each has different scrollback depth). Sync therefore keys on `tMs`. Scrollback rows are **untimestamped**, so "all panes at the same scrollback row" is meaningless — the engine pins the sync cursor to the live regime (`paintAt` only ever builds a `{kind:"live"}` moment), making a "synchronized history" state unrepresentable rather than silently wrong. [LAW:types-are-the-program] [LAW:no-silent-failure]
  - *One cursor, many inputs, never re-derived:* the shared slider AND each pane's click-to-seek bar feed the **single** `store.pos` → `store.cursorMs`; the surfaces never hold their own playhead, they read the shared one and paint, which is what keeps them in lockstep by construction. [LAW:one-source-of-truth] The per-pane paint is `.9`'s `momentBytes` (seed ++ `bytesUpTo(t)`) and playback advances each surface with `.5`'s `bytesBetween` forward delta — `.13` adds only the shared-cursor mapping and the N-pane projection, never re-stating the seed assembly or the forward-stream math. [LAW:carrying-cost]
- **Pane mirror to remote viewer** — *ships today* as the "Pane Mirror" mode of `examples/web-multiplexer/`. Pick a pane, get a shareable link, open it in a second browser, and watch that pane live and **read-only**. One dedicated server-side tmux control client taps the pane via `pipe-pane` and fans its bytes to every viewer; a `MirrorRegistry` (`server/mirror-registry.ts`) keys one tap per pane and ref-counts viewers, so N browsers share ONE source. The standalone viewer page (`mirror.html` → `web/main-mirror.tsx`) loads none of the operator app — it is a pure projection. Stresses: **multiplex breadth**, state reconciliation, input fidelity (by its absence).
  - *Read-only is a TYPE, not a flag:* the viewer's transport (`web/mirror-viewer-bridge.ts`) has `onBytes` + lifecycle state and **no** `execute`/`sendKeys`/`send` of any kind — "a projection writes back to the pane" is not a method that exists, so it cannot be called. The `/mirror-ws` endpoint accepts an EMPTY client→server vocabulary (the pane is named in the URL); an inbound frame is misuse and closes the socket. The source/projection separation the idea asks for is enforced by the shape of the types, not by a runtime check. [LAW:types-are-the-program] [LAW:single-enforcer]
  - *One source, N projections, count made visible:* the registry broadcasts `{viewers:N}` to a mirror's viewers on every change — so the count rides the viewers' OWN channel, needing no stats back-channel bolted onto the operator's `/ws` (zero changes to the existing bridge). The operator's live preview is itself just another read-only viewer, so the "👁 N watching" badge ticks up the instant a second browser opens the link. [LAW:one-source-of-truth] [LAW:decomposition]
  - *Why it could not exist without control mode:* one control client observes any pane focus-independently (`pipe-pane` taps the pty before tmux emulation; `capture-pane -e -p` seeds a late joiner's current screen) and relays it to arbitrary remote browsers without disturbing the operator. With one PTY per pane you would have to hand out the pane's fd. The per-pane FIFO tap is the same primitive the firehose uses — factored into `server/pane-tap.ts` so the tap-every-pane firehose and the tap-one-pane mirror share one implementation. [LAW:single-enforcer]
  - *Seed ordering, the .5 way:* a joining viewer is sent the `capture-pane` screen and THEN added to the live fan-out; bytes arriving in the sub-frame capture window are dropped (already baked into the captured screen) rather than double-painted — the same loss-over-double-count choice the recording demos made. A pane that closes under its viewers is detected by one shared `list-panes` liveness poll and surfaced as a `gone` frame, never a silently frozen terminal. [LAW:no-ambient-temporal-coupling] [LAW:no-silent-failure]

#### Parsing / data extraction
- **Structured data sniffer** — *ships today* as the "Data Sniffer" mode of `examples/web-multiplexer/`. A live watch over the firehose of every pane in every session pulls JSON (single- and multi-line), CSV/TSV and tables (pipe/markdown, box-drawn, and whitespace-aligned `ls -l`/`kubectl get`) out of the raw byte stream and renders each as a real table; click a block to expand its grid, click the pane to jump to it. Stresses: **parsing depth**, streaming completion. Like the Inspector and Image Extractor it is in the "consumes raw bytes, renders a non-terminal view" family — it does **not** build on `@promptctl/pane-terminal`.
  - *Detection IS a successful parse, so there is no "looks structured but unparsed" limbo:* a `SniffedBlock` (`web/data-sniff-engine.ts`) ALWAYS carries a valid `TabularData` grid — it exists only once the bytes have parsed into rows. The view never branches on "is this parseable yet"; the unparseable case is simply a block that was never emitted. [LAW:types-are-the-program] [LAW:dataflow-not-control-flow]
  - *Streaming completion is content-driven, not timing-driven:* a multi-line JSON value completes when its brackets balance (a string-aware bracket walk, so `}` inside `"…"` doesn't count); a delimited run completes when a non-conforming line breaks it. The one genuinely temporal case — the *last* table a pane prints, which no breaking line follows — is closed by **quiescence**: the store's tick (`web/data-sniff-store.ts`) owns "this pane fell silent" and asks the pure engine to finalize that one pane, so a slowly-printed table is never split into per-tick fragments. The engine itself stays a pure function of (bytes → blocks). [LAW:no-ambient-temporal-coupling] [LAW:effects-at-boundaries]
  - *Precision over recall, stated honestly:* the run-consistency requirement (≥2 consecutive rows of identical column count, ≥3 for the noisier whitespace family) is the false-positive guard — prose rarely repeats an identical column shape line after line. Whitespace-aligned tables are in scope but gated hardest; what the sniffer doesn't catch, it doesn't pretend to. [LAW:no-silent-failure]
  - *Why it could not exist without control mode:* the firehose taps every pane's pty via `pipe-pane` regardless of which session the browser is focused on, so structured data surfaces from panes you aren't even looking at — and the tap is read-only, so the sniffer sits *between* the user and the terminal, observing without injecting a byte. [LAW:single-enforcer]
- **Hyperlink (OSC 8) sidebar** — *ships today* as the "Hyperlink Sidebar" mode of `examples/web-multiplexer/`. A live watch over the firehose of every pane in every session frames `OSC 8` hyperlink escapes (`ls --hyperlink`, compiler diagnostics, many CLIs) out of the raw byte stream and collects every clickable destination into one global, deduplicated sidebar; click a link to open it, click the pane to jump to whatever emitted it. Stresses: **parsing depth**, aggregation. Like the Inspector, Image Extractor and Data Sniffer it is in the "consumes raw bytes, renders a non-terminal view" family — it does **not** build on `@promptctl/pane-terminal`. Trivial with the parser, impossible without it.
  - *Detection IS a successful parse, so there is no "looks like a link but has no target":* a `Hyperlink` (`web/hyperlink-engine.ts`) ALWAYS carries a non-empty URI — an `OSC 8` opener with an *empty* URI is, by the spec, the *closer*, so "a link with no destination" is unrepresentable. The registry holds an entry only once a non-empty URI has been framed; the view never branches on "is this a real link yet". [LAW:types-are-the-program]
  - *Finalizing a dangling link is pure upside, unlike the sniffer's:* the URI is **atomic at the opener** — fully known before any display text. So when a pane falls silent mid-link (an opener whose closer never arrived), the store's tick (`web/hyperlink-store.ts`) finalizes it on quiescence and the result is always a complete, correct link, never a half-parsed payload. The pure engine stays a function of (bytes → registry); the *store's* tick owns "is this pane quiet". [LAW:no-ambient-temporal-coupling] [LAW:effects-at-boundaries]
  - *Precision over recall, by reading the explicit marker not guessing:* we collect ONLY declared `OSC 8` hyperlinks — we deliberately do **not** heuristically auto-detect bare URLs in plain text, the false-positive swamp this avoids. `OSC 8` is an unambiguous marker the producing program emits on purpose, so every entry is a link with zero guessing. [LAW:no-silent-failure]
  - *Clickability is a security boundary, enforced in one place:* terminal output is untrusted, so a `javascript:`/`data:` URI must never become a live `<a href>` in the page origin. `isSafeScheme` in the view (`web/components/HyperlinkSidebarView.tsx`) is the ONE gate a URI passes to become clickable; an unsafe-scheme link is still *listed* (rendered as non-clickable text), never silently dropped. The pure engine stays honest and unfiltered. [LAW:single-enforcer] [LAW:no-silent-failure]
  - *Why it could not exist without control mode:* the firehose taps every pane's pty via `pipe-pane` regardless of which session the browser is focused on, so a link printed in a pane you aren't looking at still collects — and the tap is read-only, so the sidebar sits *between* the user and the terminal, observing without injecting a byte. A terminal renders an `OSC 8` link once and discards the URI; here it is collectible from every pane at once. [LAW:single-enforcer]
- **Prompt detector + command palette** — *ships today* as the "Command Palette" mode of `examples/web-multiplexer/`. A live watch over the firehose of every pane in every session chunks each shell's output into discrete *commands* — each with its command line, its (bounded) output, and its exit code — by reading the shell's `OSC 133` prompt-integration marks (`A` prompt-start, `B` command-start, `C` output-start, `D` finished-with-exit-code; the de-facto standard adopted by iTerm2, VTE, WezTerm, Kitty, Windows Terminal). Filter the global history, click a pane to jump to it, or hit **Re-run** to send a past command back to the pane it came from. Stresses: **parsing depth**, command-history extraction, the **write** axis. Like the Inspector, Image Extractor, Data Sniffer and Hyperlink Sidebar it is in the "consumes raw bytes, renders a non-terminal view" family — it does **not** build on `@promptctl/pane-terminal`. Trivial with the parser, impossible without it.
  - *A command is a SPAN between point events, so the framer is split from the interpreter:* an `OSC 133` mark is a *point* event (unlike `OSC 8`, where the URI is atomic at the opener). A command's identity is the `B→C` span; its outcome arrives at a third mark (`D`). So the resumable OSC framer (lifted from `.16`'s `OscLinkScanner`) only frames OSC strings and emits text-runs + marks; the prompt/command/output lifecycle is a state machine *on top* of it (`web/prompt-engine.ts`). One part frames, another interprets. [LAW:decomposition]
  - *Detection IS a successful parse, so there is no "maybe-a-command":* a `CommandRecord` is born only once `B→C` closes with a **non-empty** command line — Enter at an empty prompt births nothing, so "a command with no text" is unrepresentable. Its outcome is a discriminated `status` (`running` until `D`, then `finished` with the exit code `D` carries), so the palette's badge renders by exhaustive case, never by guessing from a sentinel. [LAW:types-are-the-program]
  - *Completion is an EVENT, never a timer — and so, unlike `.15`/`.16`, there is NO quiescence flush:* a command is completed by its `D` mark, or superseded by the next prompt (`A`) when `D` was dropped. A silent pane may simply be running a long command (`vim`, `sleep 60`), so finalizing on silence would be a lie — the store's tick (`web/prompt-store.ts`) only *drains*, it never finalizes. This is `[LAW:no-ambient-temporal-coupling]` cutting the opposite way from the sniffer's last-table case, and it makes the store strictly simpler.
  - *Re-run fidelity diverges from `.16` exactly where the data's purpose does:* the two demos share a scanner, but `.16`'s label is for *display* (collapses `\s+`) while this command line is destined for `sendKeys` and will be *re-executed* — so internal spacing is preserved verbatim and only the prompt indent + trailing Enter are trimmed. Collapsing `echo "a   b"` would corrupt the re-run. [LAW:types-are-the-program]
  - *Re-run is the write boundary, gated to one place and one explicit action:* `store.rerun` is the ONE path a command is written back to a live shell (`sendKeys` = `send-keys -H`, byte-for-byte + Enter), it fires only on an explicit click, and it targets the *origin* pane — the command's known context (cwd, shell). The pure engine never writes; like Smart Broadcast (`.12`) this drives a pane's **input**, but here the payload is a value lifted out of that same pane's recorded **output**. [LAW:single-enforcer] [LAW:effects-at-boundaries]
  - *Precision over recall, by reading the explicit marker not guessing:* commands are chunked ONLY from declared `OSC 133` marks — we deliberately do **not** heuristically sniff `$ `/`% `/`> ` prompts out of plain text (which misguesses on every `cat` of a config file). A shell without integration contributes zero commands, honestly reported as panes-tapped vs commands-found, never faked. [LAW:no-silent-failure]
  - *Why it could not exist without control mode:* the firehose taps every pane's pty via `pipe-pane` regardless of which session the browser is focused on, so commands run in a pane you aren't looking at still collect — and the tap is read-only, so the palette sits *between* the user and the terminal, observing without injecting a byte (the re-run is the one deliberate, user-triggered write). A terminal uses `OSC 133` to fold commands and then forgets them; here the command history of every pane is reconstructable and re-runnable at once. [LAW:single-enforcer]

#### Testing / mocking
- **Mock tmux server** — *ships today* as library surface (`@promptctl/tmux-control-mode-js/mock`) **and** as the "Protocol Tutorial" mode of `examples/web-multiplexer/`. `MockTmuxServer` is a protocol-faithful, in-process control-mode endpoint: it implements the same `TmuxTransport` interface `spawnTmux()` does, so `new TmuxClient(mockServer)` runs the *entire* library against a scripted scenario with **no tmux process, no `child_process`, no sockets**. The first deliverable is the library mock + two new pure primitives; the tutorial is its public face. This is the FIRST showcase leaf that ships *library API* rather than only a web view, and the first infra demo — it renders no pane bytes, so (per the epic constraint) it is independent of `@promptctl/pane-terminal`. Stresses: control-mode commands, parsing depth (every notification + guard-block framing).
  - *The mock IS the parser run backwards.* The library already had the wire→message direction (`TmuxParser` + `decodeOctalEscapes`); a faithful server is exactly the inverse. So two pure primitives were added to `/protocol`: `serializeMessage(msg)` (message→wire, an exhaustive `switch` over all 28 `TmuxMessage` variants) and `encodeOctalEscapes(bytes)` (the inverse of the decoder). The contract binding the two directions is a round-trip property test — `parse(serialize(m))` reproduces `m` for every variant, and `decode(encode(b)) === b` for all 256 byte values — so the inverse cannot silently drift. The exhaustive `switch` makes coverage a *compile-time* guarantee: a new message variant fails to compile until its wire form is declared. [LAW:types-are-the-program] [LAW:one-source-of-truth]
  - *Mechanism is cut clean from policy.* `MockTmuxServer` owns only the protocol-universal mechanism — monotonic command numbering, FIFO `%begin … %end`/`%error` guard-block framing (flags = 1, `CMDQ_STATE_CONTROL`, per SPEC §4), serialization, and delivery ordering. The injected `MockScenario` owns only policy — a `greeting` topology and a pure `respond(command) → CommandReply` responder (default: `ok` with no output, exactly how real tmux answers most commands). Neither half knows the other's concern; a scenario is pure data. [LAW:decomposition]
  - *A reply is a discriminated union, never a boolean.* `CommandReply = { kind: "ok" } | { kind: "error" }` — success terminates the block with `%end`, failure with `%error`, distinct by construction rather than a flag a callsite must remember to read. [LAW:types-are-the-program]
  - *Block Purity holds by construction, not by vigilance.* SPEC_MANIFEST §4.1: a notification must never land inside a `%begin`/`%end` pair. `send()` enqueues an *entire* guard block atomically, so an `emit()` can only ever fall before or after a block, never between its lines. The invariant the parser relies on is structurally guaranteed by the mock that produces it. [LAW:single-enforcer]
  - *Delivery is an explicit trampoline, never event-loop timing.* The instant `TmuxClient` sees the greeting it flips to ready and issues its bootstrap `list-panes` — synchronously, mid-delivery. A naïve "deliver on send" would re-enter the client's `parser.feed` and corrupt its line buffer. Instead `send`/`emit`/`start` only *enqueue* wire lines; a re-entrancy-guarded `flush()` drains them, so a line enqueued while another is being delivered is picked up by the outer loop and the parser is never called re-entrantly. Delivery is synchronous + deterministic; real tmux's async timing is deliberately out of scope (the chaos demo `.19` adds it as a transport decorator wrapping this clean stream). [LAW:no-ambient-temporal-coupling]
  - *The mock is pure, so the tutorial runs it in the browser.* `MockTmuxServer` imports the `TmuxTransport` type-only (erased) and depends only on `/protocol`; its emitted JS pulls zero Node deps. The "Protocol Tutorial" mode (`web/tutorial-store.ts` + `web/tutorial-scenarios.ts` + `components/TutorialView.tsx`) therefore runs a genuine `MockTmuxServer` + `TmuxParser` *in the browser tab* — touching no bridge, no firehose, no tmux — and shows the raw control-mode wire next to the parsed `TmuxMessage` events as you step a scenario or send a command. "Learn the protocol without installing tmux," and the fact that the real library mock + parser run unmodified in a tab is itself the proof they are pure. [LAW:effects-at-boundaries]
  - *Why it doubles as the integration harness:* `mock-server.test.ts` drives a *real* `TmuxClient` through greeting, command framing, FIFO correlation of concurrent commands, error rejection, `%output` byte routing to a sink, and detach — all with zero tmux, in the unit tier. If the client parses, correlates, and routes against the mock's wire, it does so against real tmux too, because the wire is the same — guaranteed by the round-trip test. [LAW:verifiable-goals]
- **Chaos mode** — *ships today* as library surface (`@promptctl/tmux-control-mode-js/chaos`) **and** as the chaos dials of the "Protocol Tutorial" mode. `withChaos(inner, opts)` is a transport **decorator** that perturbs the inbound control-mode stream — dropping, corrupting, and delaying the chunks before they reach the parser — and it wraps **any** `TmuxTransport`: the in-process `MockTmuxServer` (deterministic fuzzing in tests and the browser) or a real `spawnTmux` (chaos over live tmux). It is the live fuzzer over the parser-tolerance unit tests: where those assert "the parser survives *this* hand-written malformed line", chaos runs corruptors over a real stream to find the malformed line nobody thought to write. Builds on `.18`'s clean mock (which deliberately left async timing out so chaos could own it) and renders no pane bytes, so it is independent of `@promptctl/pane-terminal`. Stresses: parser tolerance, the command state machine under loss, the timing axis.
  - *The chaotic run is a pure function of its seed.* Chaos that cannot be reproduced is useless as a fuzzer — a failure you cannot replay is a failure you cannot fix. So randomness is a seeded `mulberry32` generator (no `Math.random()`), and the multi-seed harness prints the seed on a crash. Note the seed, replay the bug. [LAW:verifiable-goals]
  - *Decision is cut from acting.* `planChunk(chunk, params)` is a **pure** function — given a chunk and the seeded generator, it returns a description (`drop`, or `deliver` with a payload and a delay). `withChaos` is the only part that acts: it subscribes to the inner transport, runs the decision, then either drops the chunk or hands it to a `ChaosClock` for delivery. The corruptors (`truncate`, `flip-octal`, `flip-byte`, `drop-newline`, `inject-bytes`) are pure string→string mutations, each guaranteed to actually change a non-empty chunk — a corruptor that silently no-ops would be a lie to the fuzzer. [LAW:decomposition] [LAW:effects-at-boundaries] [LAW:no-silent-failure]
  - *Timing has one explicit, injectable owner.* The one effect — waiting before delivery — lives behind a `ChaosClock`: production passes nothing (a real `setTimeout` clock), tests pass a `ManualClock` and advance virtual time by hand, so delayed and reordered delivery (a later chunk with a shorter delay overtaking an earlier one) is exactly reproducible and assertable. Zero-latency delivery stays *synchronous*, preserving the mock's deterministic ordering — so drop/corrupt-only chaos needs no clock at all. [LAW:no-ambient-temporal-coupling]
  - *Chaos is inbound-only, on purpose.* `send`/`onClose`/`close` pass straight through; dropping a client *command* would desync the mock's command FIFO from the client's pending-promise FIFO — a transport-correlation failure, not the parser/state-machine stress this demo is about. The cut keeps the part doing exactly one thing. [LAW:decomposition]
  - *The harness proves the library copes, end to end.* `tests/unit/chaos.test.ts` wraps a real `MockTmuxServer` driving a real `TmuxClient` in chaos across 60 seeds of lossy, corrupt, jittered wire and asserts the parser and command state machine never throw; a focused test proves a corrupted line does not poison the well-framed line after it (buffer recovery). The same `withChaos` runs in the browser tab: the tutorial's CHAOS dials (drop / corrupt / latency / seed) replay the scenario through a genuine decorator, the wire column shows the mangled bytes the parser actually receives (corrupt lines flagged red), and a `sent · delivered · dropped · corrupted` tally makes the loss visible. [LAW:verifiable-goals] [LAW:effects-at-boundaries]
- **Conformance dashboard** — *ships today* as library surface (`@promptctl/tmux-control-mode-js/conformance`) **and** as the "Conformance" mode of `examples/web-multiplexer/`. `buildConformanceChecks()` is a catalogue of runnable propositions — one per documented SPEC §23 message, plus the command-correlation contract — each of which spins a real `MockTmuxServer` → real `TmuxClient`, drives one protocol surface, and reports green/red. Only the tmux *process* is substituted (the mock speaks the exact wire via `serializeMessage`); the parser, correlation FIFO, and sink path are the shipped library, so a green run is a real statement about the client. The third infra leaf (after `.18`/`.19`): it ships library API as the primary deliverable, renders no pane bytes, and is therefore independent of `@promptctl/pane-terminal`. Stresses: every notification + guard-block framing + the byte-sink channel, observed end to end. The demo *is* the conformance suite.
  - *Cut along the observation channel, which is the joint the client is cut on.* `TmuxClient.handleMessage` routes each message one of three ways: pane bytes (`%output`/`%extended-output`) go to the sink channel and are never emitted; the guard frames (`%begin`/`%end`/`%error`) drive the correlation FIFO and are observed by `execute()` resolving or rejecting; every other variant is emitted as an event. The catalogue mirrors that exact partition — so it is three runners (one per channel) parameterised by the canonical sample, **not** 28 hand-written cases. [LAW:decomposition] [LAW:one-type-per-behavior] [LAW:types-are-the-program]

Two messages conform iff they serialise to the same line, reusing the library's own canonical representation rather than a hand-rolled deep-equal (whose key-order would make equal messages compare unequal). A regression that surfaced a wrong field value compares unequal and the row goes red. [LAW:one-source-of-truth] [LAW:no-silent-failure]
  - *One catalogue, two columns, no twin lists.* The same `MESSAGE_SAMPLES` Record drives the deterministic suite, the serializer round-trip test (which now consumes it instead of maintaining its own copy), and the live integration column (`tests/integration/conformance.test.ts`), which holds real tmux to the catalogue's field *shape* — proving the samples are realistic and the two columns cannot drift on what a notification looks like. [LAW:one-source-of-truth]
  - *Pure, so the dashboard runs the real client in the browser.* The catalogue's heaviest import is `TmuxClient` itself, whose entire closure is browser-safe (the transport is a type-only seam). So the "Conformance" mode (`web/conformance-store.ts` + `components/ConformanceView.tsx`) runs the genuine catalogue — real client, real parser — in the tab, grouped green/red by channel with a per-row verdict, touching no bridge and no tmux. ## Selection criteria

When picking the next demo to build, prefer ones that:
1. Cover an axis no existing demo covers.
2. Can only exist because of control mode (not just "a terminal in a browser").
3. Would force a real edge case in the library API to surface.
4. Are visually obvious in 5 seconds — a screenshot should sell it.

A demo that scores 4/4 is the next thing to build. 3/4 is a strong candidate. 2/4 is filler.
